1. Problem

1.1 Definition

Modern networks generate traffic at a scale where manual inspection is simply not possible. Security teams need systems that can watch for attacks such as DDoS floods, TCP SYN storms, and port-scan probes as events are happening, not hours later in a batch report. The core challenge is building a pipeline that ingests raw network log events, computes meaningful traffic features over short time windows, and runs a machine learning model against those features, all within a few hundred milliseconds of the original event arriving.

1.2 Problem Motivation

Most intrusion detection tools in production today still rely on periodic batch processing or rule-based signature matching. Batch processing simply catches threats too late, since an attacker can saturate a link or exfiltrate data long before a nightly report surfaces the anomaly. Rule-based systems, on the other hand, require someone to write and maintain thresholds for every known attack pattern, and they are blind to anything novel.

Unsupervised ML models like Isolation Forest are well-suited to this problem because they learn what normal traffic looks like and flag deviations without needing labelled attack samples. However, most course-level projects that use Spark Streaming either skip the ML component entirely or fake it with if-else rules dressed up as a UDF. Our goal is to build the real thing: an offline-trained Isolation Forest model, serialized and broadcast into a live Spark streaming job, evaluated against actual CIC-IDS2017 network data.

1.3 Design Goals and Supported Features

  • Throughput target: the pipeline should handle at least 10,000 events per second end-to-end without falling behind the input rate.
  • Detection latency: from the moment a packet event enters Kafka, an anomaly alert should be written to storage within 500 ms (p95).
  • Genuine ML inference: a scikit-learn Isolation Forest model, trained offline on CIC-IDS2017, is broadcast to Spark workers and called via a vectorized pandas_udf. No hardcoded thresholds in the scoring path.
  • Hybrid detection: a lightweight rule check runs first for well-known attack signatures; the ML model runs in parallel to catch patterns the rules miss. Both labels are stored separately so we can compare them.
  • Scalability measurement: we vary Kafka partition count and Spark executor count independently to show how the system scales and where bottlenecks appear.
  • Live monitoring dashboard: a Streamlit UI shows current throughput, anomaly rate, and fires a retraining alert if more than 15% of recent windows are flagged.

A Python Kafka producer reads CIC-IDS2017 flow records and re-emits them as JSON events at a configurable rate. It also supports an attack injection flag so we can trigger DDoS bursts or port-scan sequences on demand during testing. On the processing side, a PySpark Structured Streaming job subscribes to the Kafka topic, groups events into 30-second sliding windows (with a 10-second slide step), and computes four aggregated features per source IP per window. Those feature rows are scored by the broadcast Isolation Forest model using a pandas_udf, which applies the model to an entire batch at once rather than row by row. The resulting records, including both the ML score and the rule-based flag, are written to Cassandra. A Streamlit dashboard polls Cassandra every few seconds and renders live charts for the operations view.

2.2 Big Data Platforms Used

  • Apache Kafka – message broker with configurable partitioning for the scalability experiments.
  • Apache Spark / PySpark – Structured Streaming with 30 s windows, MLlib pipeline, and pandas_udf for vectorized ML scoring.
  • Apache Cassandra – wide-column NoSQL store with a time-series schema; partitioned by date bucket to avoid write hotspots, using the Spark-Cassandra-Connector as the sink.
  • Docker Compose – runs the full cluster (Kafka, Zookeeper, Spark, Cassandra) on a single machine for development and benchmarking.
  • scikit-learn on Google Colab – used for the one-time offline training of the Isolation Forest model on CIC-IDS2017 data.

2.3 Data Sources and Data Models

We use the CIC-IDS2017 dataset published by the Canadian Institute for Cybersecurity. It contains roughly 2 GB of pre-computed network flow feature files in CSV format, spanning a full week of traffic with labelled examples of DDoS, DoS, Port Scan, Brute Force, Web Attack, and Infiltration. The producer reads these files and replays the flow records as streaming JSON events.

Each Kafka event carries these fields: timestamp, src_ip, dst_ip, dst_port, bytes_sent, syn_flag, ack_flag. The Spark job groups events over a 30-second window and computes four features per group: total_bytes, unique_ports, syn_ack_ratio, and packet_rate. These four values form the feature vector that the Isolation Forest scores.

Each Cassandra record stores: date_bucket (partition key, e.g. "2026-11-01"), detected_at and src_ip (clustering keys, ordered by most recent first), plus anomaly_score, rule_flag, and is_anomaly.

3. Evaluation Approach

3.1 Experiment Plan

All benchmarks run locally on a MacBook Pro (M-series, 16 GB RAM) using Docker Compose. We run three experiments, each varying one dimension at a time while holding the rest fixed. Every run lasts 10 minutes and we sample throughput and latency every 30 seconds.

Experiment What We Vary Values Held Fixed
E1 – Kafka Partitions Number of topic partitions 1, 4, 8, 16 2 Spark executors, 5,000 events/s
E2 – Spark Parallelism Number of Spark executors 1, 2, 4 8 partitions, 5,000 events/s
E3 – Attack Injection Share of malicious events 0%, 5%, 20% 8 partitions, 2 executors

Throughput is measured from Spark's streaming query listener. End-to-end latency is measured as the difference between the event timestamp in the Kafka message and the detected_at timestamp written to Cassandra. Attack injection is controlled through a command-line flag on the producer.

3.2 Performance Metrics for Success

  • The pipeline sustains at least 10,000 events/second in experiment E1 with 16 partitions.
  • p95 end-to-end latency stays below 500 ms at an input rate of 5,000 events/second.
  • Going from 1 to 4 Kafka partitions produces at least a 1.5x improvement in throughput, confirming that partition count is a meaningful scaling lever.
  • After a simulated Spark worker restart, the pipeline recovers and resumes processing within 30 seconds using Spark checkpointing.

3.3 Feature Metrics for Success

  • The Isolation Forest model achieves precision of at least 0.80 and recall of at least 0.75 on the held-out test portion of CIC-IDS2017 (Friday DDoS and Thursday Port Scan files).
  • On a clean benign-only traffic run, fewer than 5% of windows are incorrectly flagged as anomalies (false positive rate).
  • We produce a side-by-side comparison of rule-only detection versus hybrid (rule + ML) detection across each attack category in the dataset.
  • Anomaly alerts appear in the Streamlit dashboard within 5 seconds of being written to Cassandra during a normal-load run.
  • The drift alert banner in the dashboard triggers correctly when attack injection is raised to a level that pushes the anomaly rate above 15%.
